## 1. What this project is

**HunarLens** is an explainable machine-learning system for **youth unemployment vulnerability in Pakistan**.

- **Task:** binary classification. Target column `is_unemployed` (1 = unemployed, 0 = employed), for youth aged **15–24** who are in the labour force.
- **Data:** two public Pakistan Bureau of Statistics (PBS) sources: **Labour Force Survey (LFS) 2024–25** (individual records) and **Population and Housing Census 2023** (regional indicators such as population density, urbanisation, average household size).
- **Models:** `DummyClassifier` baseline + Logistic Regression + Random Forest + Gradient Boosting.
- **Primary metric:** F1-score of the unemployed (positive) class. Also precision, recall, ROC-AUC, PR-AUC (average precision).
- **Deployment:** one Streamlit app on Streamlit Community Cloud (public URL).
- **Course context:** CT-378. Marks come from lifecycle quality, a working deployment, a 3–4 page report and an **individual viva**. Three students must be able to explain every line of code, so write simple, readable code.
- **Expectation:** the positive class is a small minority and demographics only partly explain unemployment. Scores will be modest (an earlier attempt reached F1 ≈ 0.31 vs a dummy ≈ 0.12). **Honest, leak-free results beat impressive-looking ones.**

## 2. Hard rules (never break these)

**R1 — No leakage. Allowlist, not blocklist.**
Only columns listed in `src/hunarlens/config.py::FEATURES` may enter `X`. Anything describing labour-market status is forbidden as a predictor: employment status, job search, availability for work, hours worked, occupation, industry, wages, duration of unemployment, reason for not working, main activity status, and anything used to derive the label. If you are unsure whether a column is label-derived, treat it as forbidden and ask the human.

**R2 — One scikit-learn Pipeline, fitted on training rows only.**
Imputation, encoding, scaling and feature engineering live inside a single `Pipeline` + `ColumnTransformer`. Never call `fit` or `fit_transform` on validation/test/full data. The production pipeline uses scikit-learn estimators only; any custom transformer lives in `src/hunarlens/features.py`.

**R3 — Household-aware splits.**
`group_id` (household) must never appear in more than one of train / val / test, and never in more than one CV fold. Split is **70/15/15**, stratified on the target, `random_state=42`, saved to `data/processed/split_assignments.csv`. Every experiment reads that file. Never use a plain random `train_test_split`.

**R4 — The test set is opened exactly once, in Stage 8.**
Model, hyperparameters, calibration and threshold must be frozen before that. Never compute test metrics, plots or importances earlier. If it happens by accident, tell the human and log it in `docs/DECISIONS.md`.

**R5 — Tuning protocol.**
5-fold `StratifiedGroupKFold` on the **training split only**, with `RandomizedSearchCV` or `GridSearchCV`, `refit` on `average_precision`. Calibration and the decision threshold are chosen on the **validation split only**.

**R6 — Report the right metrics, always against the baseline.**
For the positive class report F1, precision, recall, PR-AUC, ROC-AUC, confusion matrix and top-10% lift. Always show the stratified `DummyClassifier` and the prevalence (the no-skill PR-AUC) next to results. Accuracy is never the headline or a selection metric.

**R7 — Reproducible and generated by code.**
`RANDOM_STATE = 42` from `config.py` everywhere. Every table goes to `reports/tables/*.csv` and every figure to `reports/figures/*.png` (dpi 200) **by code**, never typed by hand. Scripts run from the repo root.

**R8 — Privacy and licence.**
No personal identifiers in any committed file (names, phone numbers, CNIC, addresses). Raw microdata stays out of git (`data/raw/` is git-ignored) unless the licence explicitly allows redistribution. Document each dataset's source, collection method, licence and access date in `data/README.md`.

**R9 — Too good to be true means leakage until proven otherwise.**
If any metric is far above the earlier ~0.3 F1 range, or any single feature alone gives a PR-AUC above 3x prevalence, stop and investigate before continuing.

**R10 — Dependencies.**
Python **3.11**. `requirements.txt` has exact `==` pins (runtime only, so the Streamlit build stays small); `requirements-dev.txt` holds pytest/jupyter. Core libraries: pandas, numpy, scikit-learn, matplotlib, joblib, streamlit. Ask before adding any library. No deep learning. No SHAP (decided: permutation importance instead).

**R11 — Stay in scope.**
Do not edit `AGENTS.md` or `docs/IMPLEMENTATION_PLAN.md` without human approval. Record every non-trivial decision in `docs/DECISIONS.md` (date, decision, reason).

**R12 — Stop at the gates.**
Finish one stage, print the STAGE REPORT (section 5), and **stop**. Do not begin the next stage.

**R13 — Data acquisition.**
Raw data comes only from the official PBS pages (LFS "Labour Force Statistics" page and the Census 2023 detailed-results page), downloaded by `scripts/00_download_data.py`. Discover links from the landing pages; never guess or reuse remembered URLs, and never use third-party copies of the data. Write `data/raw/MANIFEST.json` (URL, access date, size, SHA-256). If the network is blocked or an archive cannot be extracted, **stop and ask the humans** to place the files in `data/raw/`.

**R14 — Weights and design variables are not features.**
Survey weights, PSU/household identifiers, record IDs and other sampling-design variables are never predictors. The weight is used only for the label reproduction test in Stage 2 (and for an optional sensitivity check if the team approves).

## 4. Coding conventions

- Python 3.11, `pathlib` for paths, type hints on public functions, no hidden global state.
- Every module starts with a header comment: **What it does / Why it exists / How to explain it in a viva.**
- Docstrings explain the *why* in plain English. Functions under ~40 lines. No magic numbers; constants live in `config.py`.
- Notebooks: markdown headers follow the ML lifecycle (EDA, preprocessing, split, modelling, tuning, evaluation, saving). No logic longer than ~15 lines inside a notebook; import from `src/`. "Restart kernel and run all" must pass. Commit notebooks **with** outputs (graders read them) but keep them small.
- Plots: matplotlib, titled, labelled axes with units, readable fonts, colour-blind-safe palette, one idea per figure.
- Naming: `snake_case`; target `is_unemployed`; group `group_id`; split column `split` with values `train`, `val`, `test`. Positive class = 1 = unemployed.
- Git: small commits like `stage-4: grouped splits + leakage tests`. Never commit `data/raw/`, virtual environments or files over 25 MB.
- Log row counts at every filter in `reports/tables/row_waterfall.csv`. Never drop rows silently.

## 7. Definitions

- **Positive class:** unemployed (`is_unemployed = 1`).
- **Prevalence:** share of positives. A random model's PR-AUC equals the prevalence (the no-skill line).
- **Lift@k%:** precision among the top k% highest-risk records divided by prevalence.
- **Operating threshold:** probability cut-off chosen on validation to maximise F1 (primary) plus a recall-oriented screening threshold (secondary).

---

## 8. Do-nots

- Do not scale, encode, impute, resample or select features before the split.
- Do not run SMOTE or any resampling outside cross-validation folds.
- Do not tune, select or peek using the test set.
- Do not use accuracy to choose models.
- Do not use the district- or province-level unemployment rate as a feature (that is label leakage).
- Do not leave `TODO`, dead code, debug prints or hard-coded absolute paths in submitted code.
- Do not pickle with a different scikit-learn version than the one pinned.
- Do not store or log any user input from the Streamlit app.
